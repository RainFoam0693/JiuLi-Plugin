# 二维码解析优化实施计划（第二阶段：截图套截图与极小码）

## 任务状态

- 类型：讨论迭代
- 状态：P0 已实施，P1 待验证
- 优先级：P0
- 前置计划：`.claude/plan/qr-code-parser-optimization.md`
- 本轮范围：针对“聊天截图中嵌套另一张截图、二维码区域很小且经历二次缩放/JPEG 压缩”的识别链路继续优化
- 约束：本文件仅制定下一阶段方案；不在本轮规划动作中修改业务代码，不访问或执行二维码载荷

## 新样本结论

用户新提供的文件是 `864 × 1920`、JPEG 4:2:0 图片。画面主体是聊天界面，其中又嵌套了上一轮的网页截图；疑似码面只占嵌套截图的一小部分，实际进入解码器前至少经历了“原页面渲染 → 第一次截图 → 聊天缩略图/转发 → 第二次截图 → JPEG 色度抽样”这一链路。

当前实现虽然已有原图、归一化、长图分区、灰度增强和固定阈值候选，但仍有四个结构性缺口：

1. `createScanRegions()` 对竖长图只做三段全宽裁剪，没有二维局部滑窗，无法把位于局部聊天气泡/嵌套截图里的极小码放大到足够模块尺寸。
2. `NORMALIZED_MAX_EDGE = 2400` 只限制缩小，不能对局部小码做受控上采样；整图上的单个 QR 模块若已小于约 2–3 像素，ZXing 很难建立稳定采样网格。
3. 固定阈值只作用于整幅增强图，局部码的像素占比过低，且 JPEG 块效应、插值和背景纹理会掩盖 finder pattern。
4. 只有 `zxing-wasm` 单引擎结论，尚不能区分“现有策略没找到有效小码”和“图中根本不存在可恢复的标准 QR 载荷”。

同时必须保留上一阶段结论：新样本里嵌套的仍是同一张高度装饰化图案。视觉上像二维码不等于包含标准 QR 数据。放大和锐化只能改善仍然存在的模块边界，不能重建已经被装饰替换、裁掉或压缩合并的数据模块。因此本轮优化应覆盖“真实有效但很小的二维码”，而不能把当前样本强行识别出一个猜测结果。

## 目标定义

1. 对聊天截图、转发截图、截图套截图中的真实小二维码建立可控的“定位 → 局部放大 → 多预处理 → 解码”路径。
2. 通过图像金字塔与二维局部窗口，使有效码进入解码器时具备足够的像素尺寸和安静区，而不对整张长图无界放大。
3. 引入独立解码器离线验证，确认失败来自策略不足还是样本不可恢复，再决定是否增加生产依赖。
4. 维持清晰码快速路径和现有返回结构，给候选数、像素数、耗时和内存设置硬预算。
5. 明确不可恢复边界：无标准载荷、定位点/时序图案严重破坏、模块已在缩放中合并或关键信息被裁掉时，必须失败且不得猜测。

## 非目标

- 不使用 OCR、生成式模型或页面上下文猜测二维码内容。
- 不把图片上传到第三方识码服务。
- 不承诺恢复艺术化伪二维码、仅保留三个装饰定位框的图案，或模块信息已经不可逆丢失的图片。
- 不为单张负样本引入 OpenCV 等重型原生依赖；依赖变更必须由独立对照实验支持。
- 不改变二维码生成、命令触发和成功消息格式。

## 待实施任务与优先级

### P0：建立真实小码基线与 ground truth

- [ ] 保存去隐私后的新样本作为负例候选，记录 `864 × 1920`、JPEG 4:2:0、截图套截图等属性，但不把“看起来像码”当作有效载荷。
- [x] 生成已知内容的标准 QR 夹具，并覆盖长截图嵌套、小码缩放与 JPEG 压缩链路。
- [ ] 覆盖 QR 码边长约 24/32/48/64/96/128 像素、不同纠错等级、1–4 像素等效模块宽度、轻度模糊和不同 JPEG 质量。
- [x] 为有效夹具固定期望文本；当前用户样本作为“二维码结构损坏、不可误报”的诊断样本。
- [ ] 记录现有实现对矩阵中每个样本的命中、耗时、候选数和峰值像素，禁止只用当前负样本评估算法。

### P0：二维图像金字塔与局部窗口

- [ ] 原图快速路径失败后，建立有限层级的图像金字塔；优先在原分辨率定位，必要时增加 0.75/0.5 倍层帮助聚合大尺度 finder pattern，禁止先把整图缩小后再寻找极小码。
- [x] 增加短边 0.62 倍、横向 3 列和纵向最多 6 行的二维重叠窗口，覆盖边缘与聊天截图局部区域。
- [ ] 为聊天截图增加“嵌套媒体区域”优先级：先扫描中部消息内容区域及高矩形度图片块，再回退到全图滑窗；这只是排序优化，不能依赖固定聊天 UI 坐标。
- [x] 每个局部窗口保留彩色信息，使用无损 PNG 中间结果，并在整图与分区策略失败后才进入局部增强。
- [ ] 对重复或高度重叠窗口做坐标级去重；同一源区域在多个金字塔层命中时只返回一份内容。
- [ ] 将窗口坐标映射回原图，日志仅记录尺寸、层级与策略，不记录图像和二维码正文。

### P0：小码受控放大与局部增强

- [x] 仅将局部窗口放大到最大边长 1000 像素，并限制详细扫描仅处理源短边 480–1400 像素的图片。
- [ ] 插值策略至少对照 `nearest` 与 `lanczos3`：前者尽量保留模块硬边，后者适合轻度缩放模糊；由夹具矩阵决定生产顺序，不凭单样本选型。
- [ ] 给裁剪补充白色安静区，宽度按候选边长比例和最小像素值共同确定，避免固定 32 像素在不同尺度下失衡。
- [ ] 在局部窗口上比较灰度归一化、轻度锐化、去噪、反色和少量阈值候选；优先加入局部自适应阈值/局部对比度 PoC，固定阈值仅作为末级兜底。
- [x] Sharp 中间结果统一使用无损 PNG Buffer，避免再次 JPEG 编码损伤模块边界。
- [ ] 当估算出的等效模块宽度小于 1 像素，或多个模块已合并成同一像素块时，直接标记为低可恢复性，不通过无界超分辨率制造虚假模块。

### P1：疑似 QR 区域定位

- [ ] 做 finder pattern 候选检测 PoC：在多尺度灰度图中搜索近似 `1:1:3:1:1` 黑白游程和三个角点的几何关系。
- [ ] 对通过几何约束的区域估算四边形，裁剪后补安静区；存在轻度透视时再执行透视矫正并送入解码器。
- [ ] finder 检测只能用于缩小搜索范围，不能作为“识别成功”；最终必须由 QR 解码器完成格式信息、版本、纠错和载荷校验。
- [ ] 若当前艺术化样本只能找到类似定位框但无法形成合法模块网格，应返回“发现疑似二维码图案但数据不可解码”，不得返回猜测文本。

### P1：独立解码器验证与选型门禁

- [ ] 建立独立离线验证脚本，同一裁剪候选至少交叉测试 `zxing-wasm` 与另一套具备 QR 定位/透视能力的实现。
- [ ] 优先评估纯 JS/WASM 或项目平台易部署方案；OpenCV/WeChatQRCode 仅作为离线能力上限对照，不能因单张图片表现直接进入生产依赖。
- [ ] 统计各引擎在有效小码矩阵上的召回率、误报率、冷启动、单图耗时、内存、安装体积与平台兼容性。
- [ ] 新引擎只有在有效夹具上显著补足 ZXing、负例不误报、资源成本可控时，才作为 ZXing 失败后的懒加载 fallback。
- [ ] 多引擎返回冲突文本时视为不可信；必须以 QR 校验通过且结果一致，或由已知 ground truth 证明正确后，才能计为成功。

### P1：预算、早停与故障隔离

- [ ] 设定单图硬预算：金字塔层数、窗口数量、每窗口增强数、放大后最大像素、总处理时限和最大结果数。
- [ ] 候选顺序建议为：原图 → 高概率嵌套图片区域 → 中等窗口 → 小窗口 → finder/透视 → 独立解码器；任一级成功即停止昂贵分支。
- [ ] 候选按批次串行或小并发处理，不同时展开所有大 Buffer；处理完成后及时释放引用。
- [ ] 单个窗口或单个解码器异常只淘汰该候选，不让整次解析崩溃。
- [x] 使用 ZXing `returnErrors` 区分普通未检测和 QR `ChecksumError`/格式校验失败，并返回针对性提示。

## 建议实现结构

下一阶段实施时，建议将 `Model/QRCodeParser.js` 的候选链路拆为以下可单测单元，避免继续扩大 `buildFallbackStages()`：

- `buildImagePyramid(buffer)`：返回有限层级及原图坐标比例。
- `createSlidingWindows(width, height, scale)`：生成带重叠和边缘覆盖的二维窗口。
- `rankCandidateRegions(...)`：优先排列疑似嵌套图片/码区，不以固定 UI 坐标硬编码。
- `upscaleRegion(region, factor, kernel)`：执行受控放大和安静区扩展。
- `buildLocalVariants(region)`：惰性生成灰度、对比度、阈值、反色候选。
- `decodeWithZXing(candidate)`：保留现有主解码器。
- `decodeWithFallback(candidate)`：仅在技术验证通过且主解码失败后启用。
- `runDecodeBudget(...)`：统一管理候选数、时间、像素与早停。

各函数携带候选元数据（层级、原图坐标、放大倍率、预处理策略），但对外仍保持 `{ code, msg, data, Result }` 兼容。

## 实施顺序

### 阶段 A：夹具和诊断

1. 建立已知载荷的截图套截图矩阵与当前用户负例。
2. 输出当前 ZXing 在各尺寸/压缩等级下的真实识别下限。
3. 用可视化调试产物确认二维码在窗口裁剪后占比、模块像素宽度和安静区；调试图不得进入日志或仓库中的公开夹具。

### 阶段 B：低风险召回提升

1. 实现二维重叠窗口和候选排序。
2. 实现局部 2×/4× 放大、动态安静区与无损中间格式。
3. 仅对失败窗口惰性应用局部增强，加入预算和早停。
4. 在有效夹具矩阵上调整窗口尺寸、步长和放大顺序。

### 阶段 C：定位与独立验证

1. 实现 finder pattern/几何定位 PoC，并验证对截图 UI 纹理的误检率。
2. 对定位成功的候选加入透视矫正。
3. 用第二解码器做离线交叉验证，形成是否引入生产 fallback 的数据结论。
4. 若两个独立引擎均无法从已裁正、模块尺寸足够的当前用户样本解码，则将其固定为不可恢复负例，不再针对它扩张参数空间。

### 阶段 D：回归与提示

1. 回归普通码、旋转码、反色码、低对比度码、透视码、多码和全部输入类型。
2. 压测连续聊天长截图，确保内存回落且事件循环不被长时间阻塞。
3. 根据失败类别调整提示：极小/压缩图片建议发送原图或单独裁剪；疑似艺术码明确可能没有可恢复数据。
4. 记录最终识别率、误报率和性能预算，再决定计划状态。

## 验收标准

### 正确性

- [ ] 已知 ground truth 的截图套截图夹具，在约定最小边长/模块像素范围内能返回完全一致的文本。
- [ ] 同一有效小码出现在不同聊天位置、不同长宽比和不同窗口边缘时均可识别，不依赖固定 UI 坐标。
- [ ] 二次 JPEG 压缩、轻度模糊和缩放插值样本达到基线约定的召回率；具体阈值在阶段 A 数据完成后锁定。
- [ ] 当前用户样本若无独立解码器可验证的载荷，应稳定返回失败且不误报。
- [ ] 多窗口、多尺度和多引擎得到的重复结果按内容与位置归一化。

### 性能与稳定性

- [ ] 清晰码继续命中原图快速路径，不创建金字塔和局部窗口。
- [ ] 困难图处理不超过约定候选数、总像素与时限；预算值由 benchmark 确定后固化为常量和测试。
- [ ] 连续处理成功、失败和损坏图片不会造成未处理异常、WASM 重复初始化或持续内存增长。
- [ ] 新策略不会降低现有普通二维码测试通过率，也不会增加无二维码/装饰图误报。

### 兼容性与安全

- [ ] Buffer、URL、Base64、Data URL、本地路径输入以及 `{ code, msg, data, Result }` 返回结构保持兼容。
- [ ] 不上传图片、不请求二维码载荷 URL、不记录原图或完整载荷。
- [ ] 若增加 fallback 依赖，其安装、锁文件、支持平台和冷启动均通过验证。

## 明确的不可恢复边界

满足以下任一条件时，算法应诚实失败，而不是继续锐化、超分或猜测：

1. 图案只是二维码风格插画，没有合法格式信息、版本信息和数据/纠错码字。
2. 三个定位框、时序图案或必要数据区域被裁掉、遮挡或装饰替换，破坏量超过 QR 纠错能力。
3. 缩放后一个像素覆盖多个模块，黑白模块发生不可逆合并；放大只会复制/插值现有像素，不能恢复原始比特。
4. 强反光、过曝、运动模糊或 JPEG 块效应使关键模块边界消失，多个可能的模块网格同样符合现有像素。
5. 多个合规解码器在已正确裁剪、补安静区和合理放大后仍无法通过 QR 校验，且没有可信 ground truth。

对这些情况，产品提示应建议用户发送二维码原图、单独裁剪码区或让发送方重新生成标准二维码。不得把视觉模型/OCR 推测、网页上下文或随机解码输出当作识别结果。

## 完成定义

截图套截图有效夹具达到锁定后的召回目标，普通码快速路径无回退，负例和当前艺术化样本不误报，资源预算有自动化测试约束，独立解码器选型有数据结论，并同步更新失败提示与测试说明后，本阶段才可标记完成。
