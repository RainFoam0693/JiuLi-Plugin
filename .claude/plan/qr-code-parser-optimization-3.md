# 二维码解析优化实施计划（第四阶段：OpenCV WeChatQRCode 本地 PoC 与准入评审）

## 任务状态

- 类型：讨论迭代
- 状态：PoC 成功，WeChatQRCode WASM fallback 已实施
- 优先级：P0 验证用户样本，P1 评估生产接入
- 前置计划：`.claude/plan/qr-code-parser-optimization.md`、`.claude/plan/qr-code-parser-optimization-1.md`、`.claude/plan/qr-code-parser-optimization-2.md`
- 当前实现：`zxing-wasm` 原图快速路径 + `@undecaf/zbar-wasm` 懒加载 fallback + Sharp 分区/放大/增强链路
- 本轮约束：只做计划，不修改业务代码；必须先完成隔离 PoC、资源与许可评审，验证成功后才能讨论生产接入

## 用户反馈与当前结论

用户确认：QQ 人物融合的白色艺术二维码已经可以由新增的 ZBar fallback 解码，但城市插画式图案仍然无法识别；用户希望获得“QQ/微信同款”的识别能力。

当前证据支持以下结论：

1. QQ 人物图已经由 ZBar 解出完整 QR 载荷，说明它属于通用引擎仍可恢复的艺术化标准 QR；这一类问题已由现有本地 fallback 覆盖。
2. 城市插画样本在 ZXing、jsQR、ZBar 中均无结果。画面虽然包含三个 finder-like 方框，但数据区被道路、建筑和景观图形替代，尚无证据证明它含有可通过 QR 校验的载荷。
3. 继续堆叠普通锐化、阈值、放大，不等于获得 QQ/微信客户端的能力；如果模块信息不存在或已不可逆丢失，任何预处理都不能恢复真实载荷。
4. 下一步最有价值的工作不是立即接入重型依赖，而是使用公开的 OpenCV `WeChatQRCode` 完成可复现的本地 PoC，判断该样本究竟是现有引擎召回不足，还是不可解码的装饰图。

## PoC 与实施结果

- 隔离安装 `opencv-contrib-python-headless==4.11.0.86` 后，`cv2.wechat_qrcode_WeChatQRCode()` 对城市插画原图成功解出 `http://weixin.qq.com/r/j0OTi_rEdbcKra7o9xad`，确认它是可恢复的艺术二维码。
- 进一步验证 `qr-scanner-wechat@0.1.3` 的 Node/WASM 构建得到同一结果；首次模型加载约 `98ms`，单次解码约 `61ms`，无需系统 Python 或原生 OpenCV。
- 生产链路采用 `ZXing → ZBar → WeChatQRCode WASM → Sharp 增强候选` 的成本递增顺序，三套引擎均按需早停。
- WeChatQRCode 通过动态 `import()` 懒加载并复用模型单例；普通二维码继续命中 ZXing，不承担约 6 MB WASM 的初始化成本。
- 当前用户截图通过插件完整链路约 `256ms` 返回相同载荷，未访问或执行该 URL。

## 能力边界：客户端能力与公开模块不是一回事

### QQ/微信客户端内部扫码能力

- QQ、微信 App 的实际扫码链路、训练数据、模型版本、预处理策略、平台专有码支持、在线服务和风控逻辑均未作为可嵌入本插件的公开 SDK 提供。
- 未经授权无法承诺、复制或声称使用“QQ/微信客户端同款”能力；不得通过反编译客户端、调用私有接口、模拟账号会话或上传用户图片到非公开服务实现。
- 客户端能够识别某张图，也不自动证明该图是标准 QR；它可能使用平台内部标记、在线识别、上下文或专有协议。

### OpenCV `WeChatQRCode`

- `WeChatQRCode` 是 OpenCV contrib 中公开的本地图像检测/解码模块，不是微信 App 扫一扫的完整客户端实现，也不包含 QQ 客户端私有能力。
- 它的公开实现可使用二维码检测模型与超分辨率模型提升复杂背景、小码和模糊码的召回，但最终仍需恢复并校验合法 QR 数据。
- 名称中的 “WeChat” 不能作为“与微信客户端效果相同”的依据。对外文案应称为“OpenCV WeChatQRCode 本地识别引擎”或“增强识别实验”，不得宣传为 QQ/微信官方扫码能力。
- 它值得作为本地能力上限对照：若完整模型链路仍不能解出城市插画样本，且没有 ground truth，应将样本判定为装饰性或不可恢复，而不是继续猜测。

## 目标定义

1. 用完整的 OpenCV `WeChatQRCode` 本地模型链路验证城市插画样本，并与当前 ZXing、ZBar 基线使用完全相同的输入和 ROI 对照。
2. 建立覆盖普通码、相机实拍、聊天截图、极小码、模糊码、透视码、艺术标准 QR、损坏码和装饰图的匿名测试矩阵。
3. 量化 `WeChatQRCode` 相对当前双引擎链路的增益、误报、耗时、内存、包体、冷启动和安装成本。
4. 完成模型文件来源、版本、哈希、许可证、再分发权和供应链风险审查。
5. 验证 macOS、Linux、Windows 以及 x64/arm64 的可安装性和运行方式；不能只在当前开发机成功。
6. 仅当 PoC 达到明确准入标准时，再制定生产接入方案；否则保持当前实现并改进失败提示。

## 非目标

- 不保证恢复没有合法 QR 数据区的插画或严重破坏的二维码。
- 不把 OCR、可见账号、页面域名、按钮文字或图片来源推断成二维码载荷。
- 不反编译 QQ/微信，不调用私有客户端接口，不模拟登录态，不绕过服务端验证。
- 不上传用户图片到第三方识码网站或未知在线 API。
- 不在本阶段把 Python、OpenCV 原生库或模型加入生产依赖。
- 不替换已经稳定的 ZXing 快速路径和 ZBar fallback，不改变 `{ code, msg, data, Result }` 返回结构。
- 不因为单张用户样本成功就直接决定接入。

## 决策原则

1. **先证明样本有载荷，再讨论恢复。** 城市插画样本必须取得生成端载荷、官方客户端扫描结果或独立引擎的完整校验结果；否则 ground truth 为 `unknown`。
2. **检测不等于解码。** 模型定位到三个角点、矩形或疑似码区，只能记为 `detected`；必须返回通过格式、版本、掩码和纠错校验的完整文本，才记为 `decoded`。
3. **正确性优先于召回。** 多引擎冲突、重复运行不稳定或结果不能与 ground truth 逐字节一致时，按失败处理。
4. **能力增益必须具有泛化性。** 准入依据是困难样本矩阵的稳定提升，而不是城市插画这一张图。
5. **生产环境不可隐式下载。** 模型和二进制必须固定版本、固定哈希、来源可审计；启动时不得从浮动 URL 下载。
6. **缺失增强能力必须可降级。** OpenCV 或模型不可用时，插件仍应保留 ZXing + ZBar 的现有功能。

### P1：Node 生产集成形态评估

按以下顺序评估，但不在 PoC 阶段接入业务代码：

1. **受维护的 Node 原生绑定**：必须包含 `wechat_qrcode`，提供 macOS/Linux/Windows、x64/arm64 预编译产物，且与项目 Node 版本 ABI 兼容。
2. **可审计 WASM 构建**：必须实测包含 DNN 与 `wechat_qrcode` 能力，并评估 WASM 内存、线程、SIMD、初始化时间和包体；仅有基础 OpenCV.js 不算满足。
3. **独立本地 helper 进程**：仅当项目能可靠分发对应二进制、设置超时和资源限制时评估；默认不采用 Python 环境作为硬依赖。
4. **用户自行编译 OpenCV addon**：作为最后选项；若安装成功率和维护成本不可控，则不进入默认依赖。

无论采用哪种形态，都必须满足：按需懒加载、单例初始化、缺失时可降级、异常隔离、无网络依赖、结果结构统一。

### P1：资源预算与执行隔离

PoC 必须先测量，再锁定具体数值。生产评审至少包含以下预算：

- 模型与二进制安装体积上限，以及压缩包/解压后体积。
- 首次模型初始化时间与后续热调用时间。
- 单张普通图、困难图和长截图的 p50/p95 耗时。
- 进程 RSS、外部内存和单张峰值增量；连续 100 张后内存必须回落或趋于稳定。
- 单图最大输入像素、送入 DNN 的最大边长、ROI 数、并发数和总超时。
- 原生崩溃或超时的隔离方式；若 addon 可能拖垮主进程，应优先 worker/helper，并能强制终止单次任务。

建议候选链路保持成本递增：

`ZXing 原图 → ZBar 原图 → 现有 Sharp 低成本候选 → WeChatQRCode 单次规范化图 → 少量高概率 ROI`

禁止让 `WeChatQRCode` 对现有 18 个窗口和所有阈值候选做笛卡尔积扫描。普通清晰码必须在进入 DNN 前早停。

## PoC 数据表设计

每个样本输出一行机器可读记录：

| 字段 | 含义 |
| --- | --- |
| `sampleId` | 匿名样本 ID |
| `class` | `standard` / `camera` / `art-standard` / `damaged` / `decorative` / `unknown` |
| `engine` | ZXing / ZBar / QRCodeDetector / WeChatQRCode |
| `variant` | 原图或确定性 ROI/预处理名称 |
| `detected` | 是否定位疑似码区 |
| `decoded` | 是否返回通过校验的载荷 |
| `payloadSha256` | 载荷哈希，不保存用户明文 |
| `groundTruthMatch` | 是否与已知载荷完全一致；未知时为 `null` |
| `initMs` / `decodeMs` | 初始化与单图耗时 |
| `rssPeakMb` | 峰值常驻内存 |
| `errorClass` | 未定位、校验失败、模型失败、超时或崩溃 |
| `environment` | OS、架构、Node/Python、OpenCV、模型 commit |

报告只汇总命中率、误报率和资源数据；不得提交用户原图、QQ 号、头像、昵称、明文好友链接或 token。

## 结果决策表

| PoC 结果 | 结论 | 后续动作 |
| --- | --- | --- |
| 完整 `WeChatQRCode` 解出城市图，且与可信 ground truth 一致 | 可恢复标准/艺术 QR | 继续做矩阵与生产准入评审，不能直接接入 |
| 能检测 finder-like 区域但无法解码 | 损坏或装饰图候选 | 保持失败，不把检测框当识别结果 |
| QQ/微信客户端能扫，公开 `WeChatQRCode` 与标准引擎均失败 | 平台专有码或客户端私有能力候选 | 提示使用对应客户端；不逆向、不模拟 |
| 客户端和公开引擎都失败，且无生成端载荷 | 装饰性或不可恢复图案 | 固定为负例，停止继续扩张参数 |
| 新引擎只改善一张样本，矩阵无稳定增益 | 不具备泛化价值 | 不接入生产 |
| 有明显增益但体积、平台、许可或资源不达标 | 工程不可接受 | 保留离线诊断或设计为独立可选组件 |
| 正确性、资源、平台、许可全部通过 | 满足准入 | 另建执行计划，最小化接入为末级 fallback |

## 实施顺序

### 阶段 A：证据固定

1. 获取城市插画原始导出图及 QQ/微信扫码结论。
2. 对所有用户样本脱敏编号，只保存必要元数据和载荷哈希。
3. 锁定 PoC 样本矩阵与现有 ZXing + ZBar 基线，测试过程中不得按结果随意更换样本。

### 阶段 B：本地能力 PoC

1. 在隔离临时环境安装固定版本的 OpenCV contrib 能力。
2. 从固定官方来源取得四个模型并校验哈希。
3. 验证 `WeChatQRCode` 完整模型链路，输出检测、解码、正确性和资源记录。
4. 对相同输入复跑 ZXing、ZBar、`QRCodeDetector`，形成公平对照。

### 阶段 C：工程可行性评审

1. 评估 Node 原生绑定、WASM、helper 三种形态，不预设 Python sidecar 为生产方案。
2. 完成目标 OS/架构矩阵、安装体积、冷启动、内存、连续处理和异常隔离测试。
3. 完成 OpenCV、contrib 模块、绑定和模型文件的许可/再分发/供应链审查。
4. 给出“默认接入 / 可选增强 / 仅离线诊断 / 不接入”之一的书面结论。

### 阶段 D：后续实现（仅在用户确认且准入通过后）

1. 另建实施计划，把通过验证的引擎作为末级懒加载 fallback。
2. 实现单例模型加载、硬预算、超时、故障隔离和缺失依赖降级。

## 预计实验产物

- `scripts/qr-wechat-poc.*`：隔离 benchmark，不由插件业务入口调用。
- `test/fixtures/qrcode/manifest.json`：匿名样本信息、ground truth 哈希和授权状态。
- `docs` 或 `.claude/plan` 下的 PoC 报告：版本、模型哈希、平台、召回、误报、耗时、内存、体积和决策。
- 临时调试检测框：只保存在受控临时目录，完成分析后不进入仓库。

本阶段计划本身不创建以上产物，也不修改 `Model/QRCodeParser.js`、`package.json`、测试或锁文件。

## 验收标准

### 能力结论

- [ ] 能用证据解释城市插画样本是“可由公开引擎恢复的 QR”“损坏 QR”“平台专有码候选”还是“装饰图/未知”，不再用肉眼外观作结论。
- [ ] `WeChatQRCode` 使用检测与超分模型的完整链路运行，模型版本、来源和哈希可复现。
- [ ] 与当前 ZXing + ZBar 及基础 `QRCodeDetector` 在同一输入上完成公平对照。
- [ ] 所有成功结果与 ground truth 完全一致；未知载荷样本不计入正确识别率。

### 工程结论

- [ ] 给出安装体积、首次/热调用耗时、p95、峰值 RSS、连续处理和超时数据。
- [ ] 给出 macOS/Linux/Windows、x64/arm64、Node 版本的支持矩阵和明确降级方案。
- [ ] 给出 OpenCV、contrib、绑定、二进制和四个模型的许可及再分发结论。
- [ ] 明确选择“默认接入 / 可选增强 / 仅离线诊断 / 不接入”，并说明未选择其他方案的证据。

### 安全与隐私

- [ ] 不调用 QQ/微信私有接口，不逆向客户端，不上传用户图片，不自动访问二维码载荷 URL。
- [ ] 测试与日志不保存用户图片、QQ 号、昵称、头像、明文好友 URL 或 token。
- [ ] 装饰图、损坏码和结果冲突不会返回猜测文本。
- [ ] 模型、二进制和依赖全部固定版本与哈希，运行时不隐式联网下载。

## 停止条件

满足以下任一条件，本阶段应停止生产接入：

1. 城市插画没有可信 ground truth，且完整 `WeChatQRCode` 与其他独立引擎都不能通过 QR 校验。
2. 只有 QQ/微信客户端能识别，但不存在公开、获授权、可本地嵌入的能力。
3. 新引擎对预先锁定的困难码矩阵没有稳定增益，或负例出现误报。
4. 模型文件的授权或再分发权不明确，依赖/二进制来源无法审计。
5. 任一主平台需要用户手工编译、安装 Python/系统 OpenCV，或导致插件安装失败。
6. 包体、冷启动、CPU、内存、超时或原生崩溃风险超过本插件可接受预算。

停止接入不是放弃识别问题，而是确认公开通用二维码能力的边界。产品应诚实提示用户发送标准二维码原图，或对平台专有码使用 QQ/微信内置扫一扫。

## 完成定义

本阶段仅在以下内容全部完成后结束：城市样本 ground truth 状态明确；完整 OpenCV `WeChatQRCode` PoC 可复现；多引擎与困难样本矩阵对照完成；模型、依赖、跨平台、许可和资源预算评审完成；最终形成明确的接入决策。在此之前，不得修改生产解析链路或宣称已经拥有 QQ/微信同款识别能力。
