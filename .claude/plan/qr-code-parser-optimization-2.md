# 二维码解析优化实施计划（第三阶段：艺术码与平台专有码边界）

## 任务状态

- 类型：讨论迭代
- 状态：独立解码器验证完成，ZBar WASM fallback 已实施
- 优先级：P0 先判定样本类型与可解性，P1 再决定是否增加解码器
- 前置计划：`.claude/plan/qr-code-parser-optimization.md`、`.claude/plan/qr-code-parser-optimization-1.md`
- 本轮范围：验证两类高度艺术化图案的真实可解性，形成标准 QR、可恢复艺术 QR、平台专有码和纯装饰图的明确边界
- 约束：本文件只制定计划；不修改业务代码，不自动访问载荷，不把界面文字或账号信息猜成二维码内容

## 新样本与当前基线

### 样本 A：城市插画式二维码图案

- 文件为 `881 × 1920` JPEG 长截图，主体是城市/建筑插画，画面中有三个类似 QR 定位框的装饰图形。
- 图案缺少肉眼可确认的规则模块网格、时序图案、格式信息和连续安静区；道路、建筑、树木等插画元素占据通常应为数据模块的位置。
- 它可能是“二维码视觉隐喻”或仅保留定位框外观的广告插画，不能因为存在三个方框就认定含有 QR 载荷。
- 当前 `zxing-wasm` 经过原图、归一化、分区、二维局部窗口、放大和阈值候选后约 `1.4s` 返回无有效结果。

### 样本 B：QQ“我的二维码”人物融合艺术图

- 文件为 `864 × 1920` JPEG，来自 QQ“我的二维码”页面，人物大图覆盖常规 QR 数据区，肉眼几乎看不到标准黑白模块。
- 页面文案“扫一扫加我为好友”和显示的 QQ 号，只能证明产品意图，不能证明图片遵循公开 QR 标准，也不能证明显示账号就是图中编码载荷。
- 该图可能属于三种情况：底层仍有弱可见标准 QR 网格；QQ 客户端使用专门训练的视觉解码器；或使用未公开的平台专有码/服务端识别流程。
- `zxing-wasm` 与 `jsQR` 均返回无有效结果；独立的 ZBar WASM 对完整截图成功解出经完整校验的 `https://qm.qq.com/q/jDTJq91mpO`，耗时约 `59ms`，证明它是可恢复的艺术化标准 QR，而不是只能由 QQ 识别的私有码。

### 已完成的选型结论

- 城市插画样本在 ZXing、jsQR、ZBar 三套独立引擎中均无结果，继续作为装饰性或不可恢复负例。
- QQ 人物艺术码由 ZBar 成功解码，且结果来自图像解码而非页面文字或 QQ 号推断。
- `@undecaf/zbar-wasm@0.11.0` 体积较小、无 OpenCV 原生编译依赖，可作为 ZXing 原图失败后的懒加载 fallback。
- 生产实现保留 ZXing 快速路径；仅失败时动态导入 ZBar，ZBar 仍失败后再进入原有图像增强流水线。

## 核心判断原则

1. **“像二维码”不等于 QR Code。** finder-like 图形只能作为疑似区域定位信号，最终成功必须由合规解码器通过格式、版本、掩码和 Reed–Solomon 纠错校验。
2. **“QQ 能扫”不等于通用解码器应能扫。** 若只有 QQ 客户端能识别，必须先确认它是标准 QR 的特殊渲染，还是平台私有码；两者的实现与合规边界完全不同。
3. **可见文字不是载荷。** 禁止 OCR QQ 号、用户名、页面链接或根据上下文拼接 `mqqapi`/URL 后作为识别结果返回。
4. **没有 ground truth 就不能宣称成功。** 样本结果必须与原始生成端、QQ 官方扫码结果或已知夹具载荷逐字节一致。
5. **解码器冲突时宁可失败。** 任意引擎返回校验错误、空结果或彼此冲突的文本，不得通过投票、语义合理性或账号匹配强行选值。

## 目标定义

1. 用独立实现验证现有失败究竟来自 ZXing 召回不足、艺术化导致标准 QR 受损，还是平台专有编码。
2. 建立标准 QR、艺术化但仍合规的 QR、不可恢复装饰图、QQ 专有码四类样本矩阵和可复现结论。
3. 量化 OpenCV `WeChatQRCode` 对小码、模糊、透视和艺术 QR 的增益，同时评估模型文件、原生依赖、跨平台、冷启动和内存成本。
4. 只有在真实标准载荷上显著提升召回且误报、性能、部署均达标时，才规划生产 fallback。
5. 对平台专有码形成明确产品决策：有公开且获授权的本地解码能力才支持；否则给出准确提示，不逆向、不猜测。

## 非目标

- 不保证恢复任意 AI 艺术二维码、二维码风格插画或已经丢失模块的截图。
- 不使用 OCR、视觉大模型、搜索引擎或页面上下文推断二维码载荷。
- 不把图片上传至第三方识码网站，不自动用外部 App 扫描用户图片。
- 不反编译 QQ 客户端、不模拟私有接口、不绕过签名或服务端校验。
- 不因为单张样本有效就直接引入 OpenCV、Python sidecar 或大型模型文件。
- 不改变现有命令、返回结构、二维码生成逻辑和成功消息格式。

## 待实施任务与优先级

### P0：取得可信 ground truth 与样本分类

- [ ] 请求样本提供者用 QQ 内置“扫一扫”直接扫描样本 B，并记录**扫码得到的原始结果类型**（加好友卡片、内部 token、URL 或失败）；只保存脱敏后的类型与哈希，不在日志记录账号/token。
- [ ] 尽量取得样本 B 从“分享/保存二维码”导出的原图，避免以 864px 截图代表生成端原始质量；截图版与导出版分别编号。
- [ ] 对样本 A 查明原始来源是否宣称它可扫码；若没有生成端载荷或任何独立扫码器能成功，将其定义为装饰图负例，而不是待破解二维码。
- [ ] 每个有效样本固定载荷的 SHA-256 与长度；自动化断言使用完整载荷或测试专用替代样本，不用“包含 QQ 号”等宽松条件。
- [ ] 建立四类标签：`standard-qr`、`art-qr-standard-payload`、`platform-proprietary-code`、`decorative-or-unrecoverable`；未验证样本标记为 `unknown`，不得提前归类。

### P0：独立解码器离线能力验证

- [x] 建立一次性 PoC，对完全相同的原图与 ROI 比较 `zxing-wasm`、`jsQR` 与 ZBar WASM。
- [ ] `WeChatQRCode` 测试同时覆盖其检测模型和超分模型，记录所用 OpenCV 版本、模型文件版本/哈希、来源及许可证；缺少模型时不得把退化路径当成完整能力。
- [ ] 每个引擎依次测试：原图、人工确定 ROI、补安静区、透视校正、有限尺度放大、灰度/颜色通道和自适应二值化；成功后立即停止，不做无界参数搜索。
- [x] 加入已知载荷普通码、嵌套小码、损坏码和无二维码负例，并保留城市插画作为本地人工负例验证。
- [ ] 输出召回率、误报率、错误类型、定位框、耗时、峰值 RSS 和冷启动；报告中只记录载荷哈希、长度与结果一致性，不记录明文载荷。
- [ ] 若所有标准解码器都能定位但无法通过纠错校验，将样本标为“结构存在但不可恢复”；若无法形成合法模块网格，则标为“装饰/未知专有码候选”。

### P0：QQ 专用艺术码验证

- [ ] 使用“QQ 原始导出图 + QQ 官方扫码结果”建立对照；另用系统相机、微信、标准 ZXing 和 WeChatQRCode 扫描，区分“普遍可解”与“仅 QQ 可解”。
- [x] ZBar 在当前 QQ 截图上直接返回完整、稳定载荷，将样本按“艺术化标准 QR”处理并接入本地 fallback。
- [ ] 如果只有 QQ 能识别，检索是否存在公开协议、公开 SDK 或允许本地使用的官方能力；没有公开且获授权方案时，将其划为平台专有码，不进入通用二维码解析器实现。
- [ ] 不使用页面展示的 QQ 号构造返回值；即使扫码结果最终指向该账号，也必须以图像解码得到的完整 token/URI 为准。
- [ ] 若平台识别依赖账号状态、在线服务、时效 token 或风控，产品提示应说明“需使用 QQ 扫一扫”，不得伪装成本地解码失败可通过继续锐化解决。

### P1：生产 fallback 的准入门禁

仅当 P0 证明新引擎能解出**已确认是标准 QR 载荷**的困难样本，才评估接入。准入条件如下：

- [ ] 困难标准/艺术 QR 测试集的召回率相对现有 ZXing 有稳定且可重复的提升，普通码无回退，全部负例零误报。
- [x] 新引擎只作为 ZXing 失败后的懒加载 fallback；现有原图快速路径和 `{ code, msg, data, Result }` 保持不变。
- [ ] 多引擎结果必须通过各自完整 QR 校验；结果冲突时返回“不可信/无法确认”，不自动选择看起来更合理的文本。
- [ ] 为候选数量、总像素、总耗时、并发和内存设置硬预算；超限时安全退出，不能阻塞机器人事件循环。
- [ ] 新依赖在项目实际支持的 macOS、Linux、Windows 和 CPU 架构上完成安装/启动验证；任何平台需本机编译都必须有明确构建与降级方案。
- [ ] 模型与二进制的许可证、再分发权、来源校验和更新机制通过审查，不能在安装时从未经固定版本的地址隐式下载。

## OpenCV / WeChatQRCode 重点验证项

`WeChatQRCode` 的价值主要是 DNN 检测与超分辨率对小码、模糊和复杂背景的召回提升；它仍需最终恢复可校验的 QR 模块，不能把任意三定位框插画或未知 QQ 私有码变成合法 QR 载荷。因此它应作为“能力上限对照”，而不是预设答案。

| 评估项 | 必须记录 | 不通过时的结论 |
| --- | --- | --- |
| 解码正确性 | 与 ground truth 完全一致、纠错成功、重复运行稳定 | 不接入 |
| 负例误报 | 城市插画、人物图、随机纹理、损坏码均不得返回载荷 | 不接入 |
| Node 集成 | 原生 addon / 子进程 / WASM 的接口与故障隔离 | 无稳定方案则仅保留离线诊断 |
| 安装体积 | OpenCV 二进制、contrib 模块、四个模型文件及锁文件增量 | 成本超过收益则不接入 |
| 冷启动与内存 | 首次加载、后续单图耗时、峰值 RSS、并发退化 | 超预算则不接入或改为可选能力 |
| 平台兼容 | macOS/Linux/Windows、x64/arm64、Node 当前版本 | 任一主平台失败则不设为硬依赖 |
| 供应链与许可 | 包维护状态、模型来源/哈希/许可、预编译二进制来源 | 无法审计则不接入 |

候选部署形态按以下顺序评估：

1. 维护活跃且有受支持预编译产物的 Node 绑定，可懒加载并在缺失时回退 ZXing。
2. 可审计的 WASM 构建，前提是包含所需 contrib/模型能力且体积、内存可接受。
3. Python/OpenCV 子进程仅作离线 benchmark；除非项目本来就保证 Python 与依赖，否则不作为默认生产方案。
4. 本机构建 OpenCV 的 addon 成本最高，不应为两张未证实可解的样本引入。

## 分类决策表

| 验证结果 | 分类 | 产品行为 |
| --- | --- | --- |
| ZXing 或独立标准引擎返回与 ground truth 一致的载荷 | 标准/艺术化标准 QR | 可进入 fallback 准入评估 |
| 能定位模块网格，但多个标准引擎均校验失败 | 损坏或不可恢复 QR | 提示发送原始导出图/重新生成 |
| 仅 QQ 官方客户端能识别，且无公开获授权解码能力 | QQ 平台专有码 | 明确提示需使用 QQ 扫一扫，不纳入通用解析器 |
| 无模块网格、无生成端载荷、任何独立扫码器均失败 | 装饰性伪码 | 稳定返回未识别，不继续扩大参数 |
| 结果冲突或缺少 ground truth | 未知 | 保守失败并请求原图/验证信息 |

## 建议实验产物（实施阶段）

- `scripts/qr-decoder-benchmark.*`：离线运行多引擎，不被业务入口调用。
- `test/fixtures/qrcode/manifest.json`：记录匿名样本 ID、类别、尺寸、压缩链路、ground-truth 哈希和许可状态。
- `test/QRCodeParser.test.js`：只在选型完成后加入生产回归；平台专有码和装饰图应是“不误报”负例。
- benchmark 报告：包含环境、版本、模型哈希、召回/误报/耗时/RSS 与接入结论，不包含用户账号、原图或明文 token。

含个人头像、QQ 号、昵称或好友 token 的用户截图不得直接提交仓库。测试夹具应由授权的测试账号重新生成并去标识化，或用可公开再分发的合成样本替代。

## 实施顺序

### 阶段 A：证据固定

1. 获取两类样本的原始导出版本与可信扫码结果。
2. 对样本做脱敏编号和载荷哈希，确认是否允许进入私有测试资产。
3. 建立普通 QR、艺术标准 QR、专有码候选、装饰图四类基线。

### 阶段 B：离线多引擎 PoC

1. 固定 ROI 和预处理候选，复跑 `zxing-wasm` 作为基线。
2. 依次测试独立 ZXing、OpenCV `QRCodeDetector`、`WeChatQRCode` 完整模型链路。
3. 记录每类样本的检测、校验、载荷一致性、耗时、内存及错误类型。
4. 针对 QQ 样本完成“官方能扫 / 通用能扫”二维对照并分类。

### 阶段 C：选型评审

1. 若新引擎只对当前未知/专有码有效但无公开集成依据，停止接入。
2. 若其对一组标准困难码显著增益，完成 Node 部署形态、平台矩阵、许可和供应链评审。
3. 明确决定：不接入、仅提供可选诊断能力，或作为懒加载生产 fallback；结论写回计划和 benchmark。

### 阶段 D：后续实现（需用户确认后另行执行）

1. 仅按选型结论接入最小 fallback，不重写已稳定的 ZXing 快速路径。
2. 加入预算、超时、错误隔离、结果冲突策略和诊断分类。
3. 扩充回归、跨平台安装测试及隐私/日志检查。
4. 更新用户提示，分别覆盖图片质量不足、不可恢复艺术码和 QQ 平台专有码。

## 验收标准

### 研究结论

- [ ] 两张新样本都有明确的 ground truth 状态：已知载荷、仅平台可识别、确认装饰图或仍未知；不得用猜测替代。
- [ ] `WeChatQRCode` 使用完整模型链路完成可复现实验，并与至少两个独立标准 QR 解码实现对照。
- [ ] QQ 样本完成官方客户端与通用解码器的交叉测试，能说明“艺术标准 QR”还是“平台专有码候选”。
- [ ] 选型报告同时给出成功率、误报率、耗时、内存、体积、平台和许可，不以单张图成功作为接入依据。

### 安全与正确性

- [ ] 城市插画、人物图和损坏码不会返回 OCR/推测文本，不会把页面展示的 QQ 号当载荷。
- [ ] 二维码内容不被自动访问或执行；benchmark 和日志不记录明文载荷、账号、头像或原始用户图片。
- [ ] 任何生产结果都必须来自通过完整校验的解码器；冲突、超时和未知类型均安全失败。
- [ ] 不使用未经授权的 QQ 私有协议、客户端逆向或第三方在线识码服务。

### 生产接入（若最终选择接入）

- [ ] 清晰码继续由 ZXing 快速路径处理，耗时无明显回退。
- [ ] fallback 对锁定的困难标准码矩阵有显著增益，全部负例零误报，并受候选/像素/时间/内存预算约束。
- [ ] 支持平台安装、冷启动、连续处理和缺失依赖降级全部通过；新增二进制及模型来源可审计。
- [ ] 现有输入类型、命令行为和 `{ code, msg, data, Result }` 返回结构保持兼容。

## 停止条件

满足以下任一条件，应停止继续堆叠锐化、阈值和超分策略：

1. 样本 A 没有可信生成端载荷，且多个独立标准解码器都无法形成合法 QR 模块网格。
2. 样本 B 只有 QQ 官方客户端能识别，同时不存在公开、获授权、可本地部署的解码方案。
3. 已正确裁剪且模块像素充足的候选仍在多个引擎中一致校验失败。
4. 新解码器只改善单张样本，对标准困难码矩阵没有稳定收益，或引入不可接受的误报。
5. 原生依赖、模型许可、安装体积、跨平台或内存成本超过本插件的可接受范围。

停止不代表功能缺陷未处理，而是确认了通用二维码解析器的技术和产品边界。此时正确行为是返回明确失败提示，并建议用户发送标准二维码原图，或对 QQ 专有码使用 QQ 内置扫一扫。

## 完成定义

完成 ground truth 固定、多引擎 PoC、QQ 专有码分类、部署/许可评审和选型结论；所有报告不泄露用户数据，并明确给出“接入 / 不接入 / 可选能力”决策后，本阶段规划才可标记完成。任何业务代码实现需在用户确认该结论后另行执行。
