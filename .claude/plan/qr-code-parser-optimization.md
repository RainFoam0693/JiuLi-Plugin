# 二维码解析优化实施计划

## 任务状态

- 类型：需求规划
- 状态：第一阶段已实施；用户样本确认为不可解码的二维码风格插画
- 优先级：P0
- 影响范围：二维码解析模型、解析入口的错误提示、自动化测试与样本库
- 约束：不改变现有二维码生成功能；不访问、跳转或执行二维码内容

## 背景与现状结论

现有解析链路位于 `Apps/QRCodeParser.js` 与 `Model/QRCodeParser.js`：入口负责取得当前消息、引用消息或上下文补发的第一张图片，模型将完整图片原样交给 `zxing-wasm`，仅限定 `QRCode` 并开启 `tryHarder`。项目已经依赖 `sharp@0.33.5`，但解析流程尚未使用任何方向归一化、区域定位、裁剪、缩放、对比度增强、二值化、去噪或透视矫正。

用户样本是 `1280 × 2788` 的长截图，二维码式图案只占页面中部，周围包含状态栏、广告、文字、按钮和浏览器工具栏；码面还存在旋转/斜视、彩色低对比度、艺术化模块及大量背景纹理。当前实现对该原图返回 0 个结果。诊断中已尝试 ZXing 去噪、禁用降采样、区域裁剪、2 倍放大、灰度归一化、锐化、多个固定阈值、旋转及 RGB 单通道，仍未解码，说明问题不只是 `tryHarder` 参数不足，必须先确认样本确实包含可恢复的标准 QR 载荷，再重点处理码区定位、几何矫正和受控的多策略解码。

## 目标定义

1. 提升长截图、小码、低对比度、轻度模糊、反色、旋转和透视二维码的识别率，用户样本作为首要回归样本。
2. 保持 URL、Base64、Buffer、本地文件等现有输入方式和成功返回结构兼容。
3. 用“原图快速路径 → 定位/裁剪 → 几何及像素增强 → 解码”的分级策略控制延迟和内存，识别成功即提前结束。
4. 区分“没有二维码”“检测到疑似码但无法解码”“图片无效/下载失败”，让失败信息可操作。
5. 建立可重复的困难样本测试集和性能上限，避免为单张图片优化后破坏普通二维码及机器人稳定性。

## 非目标

- 不自动打开二维码中的链接，不发起二维码载荷指向的网络请求。
- 不把图像上传到第三方识码服务。
- 不承诺从并非标准 QR、数据区域严重缺失或只有装饰性 QR 外观的图片中恢复不存在的内容。
- 本轮不重构二维码生成模块 `Apps/QRCode.js` / `Model/QRcode.js`。

## 功能分解

### 1. 样本基线与有效性门禁

- [ ] 将用户样本以去隐私、稳定文件名的形式纳入测试夹具，记录尺寸、格式、期望载荷和来源类型（整屏截图/艺术码）。
- [x] 使用多组 ZXing 参数与图像增强交叉验证；样本不具备标准 QR 模块网格且始终无有效载荷，验收目标改为“准确诊断，不误报”。
- [ ] 建立普通清晰码、长截图小码、旋转码、透视码、低对比度码、反色码、多码、无二维码图片和损坏图片的基线矩阵。
- [ ] 记录现状识别率与单张耗时，作为优化前对照；用户样本当前基线为 ZXing 返回 0 个结果。

### 2. 输入安全与图像归一化

- [x] 在现有字节大小限制之外限制 Sharp 解码像素数，应用 EXIF 自动方向，统一输出到 sRGB。
- [x] 增加 50 MP 解码像素总量上限，防止压缩炸弹或超大长图导致内存峰值。
- [x] 保留原图候选作为第一条快速路径；仅在失败后构造增强候选。
- [ ] 对下载响应继续保留超时、重定向、类型及 15 MB 限制，并为无法被 `sharp` 解码的输入返回清晰错误。

### 3. 分级候选生成

- [x] 第 0 级：原图直接解码，显式启用 `tryHarder`、`tryRotate`、`tryInvert`、`tryDenoise` 和自动降采样。
- [x] 第 1 级：生成方向归一、灰度、自动对比度/归一化、轻度锐化及去噪候选。
- [x] 第 2 级：对长截图生成有重叠的中心/分区裁剪，并为每个裁剪补充安静区。
- [x] 第 3 级：对候选尝试 96、128、160、192 四档固定阈值，不做无界参数穷举。
- [ ] 第 4 级：加入 QR 定位点检测，基于三个 finder pattern 估算码区四边形，执行旋转/透视矫正后再解码；这是支持用户艺术化斜视样本的核心步骤。
- [ ] 每级识别成功立即停止后续增强；多码模式对结果按内容及位置去重后继续返回所有有效二维码。

### 4. 解码器与几何方案选型

- [ ] 优先复用 `zxing-wasm` 和 `sharp`，抽出统一的 `decodeCandidate`、`buildCandidates`、`normalizeResults`，避免把预处理逻辑堆在 `parse()` 中。
- [ ] 用用户样本验证仅靠现有依赖能否完成 finder 定位及透视校正；Sharp 适合像素处理，但不提供完整 QR finder/透视检测链路。
- [ ] 若现有依赖无法通过困难样本，做一个小型技术验证，对比“带 QR 定位/透视能力的纯 JS/WASM 解码器”与 OpenCV WeChatQRCode 类方案，评价识别率、安装体积、原生依赖、平台兼容性、冷启动及维护成本。
- [ ] 只有候选方案在用户样本和回归矩阵上显著优于现有 ZXing 时才引入新依赖；禁止为无有效载荷的样本增加重型依赖。
- [ ] 新解码器只能作为失败后的本地 fallback，返回结果仍必须经过格式、文本和去重归一化，不改变上层接口。

### 5. 资源预算与可观测性

- [ ] 设置每张图片的最大候选数、最大边长/像素数和总处理时限；达到预算后返回可理解的失败信息，不能阻塞机器人事件循环。
- [ ] 候选按“成本低、成功概率高”排序并串行早停，避免并行展开多个大图造成内存放大。
- [ ] 日志仅记录输入尺寸、耗时、成功策略、候选数量和结果数量，不记录完整二维码文本或原始图片，避免泄露敏感载荷。
- [ ] 在 debug 级别记录失败阶段（未定位/定位后解码失败/预算耗尽），正常回复不暴露内部堆栈。

### 6. 用户反馈与兼容性

- [x] 维持 `code`、`msg`、`data`、`Result` 返回字段以及成功消息格式，确保现有调用方无须修改。
- [ ] 将失败分为：没有发现二维码、发现疑似二维码但图像质量或艺术化程度导致无法解码、输入/下载/图片解析错误。
- [x] 失败时提示用户发送清晰原图或裁剪二维码区域，并明确过度美化图案可能不含可恢复数据；不伪造识别内容。
- [ ] 保留当前消息图片、引用图片和补发图片三种交互；补充多图处理策略的测试，至少保证现有取第一张图片的行为不回退。

## 实施步骤

### 阶段 A：固定基线与技术验证

1. 创建测试目录和困难样本清单，先为当前 `QRCodeParser.parse()` 补充输入类型、错误路径及普通二维码回归测试。
2. 对用户样本完成第三方基准解码，取得唯一的期望载荷；没有 ground truth 时不得把随机/错误文本当作成功。
3. 编写离线 benchmark，输出每个策略的命中结果、耗时和峰值候选尺寸；不把二维码正文写入日志快照。
4. 用 benchmark 验证 ZXing 参数、Sharp 预处理、区域扫描与透视方案，确定最小可行策略集及是否需要 fallback 依赖。

### 阶段 B：重构解析内核

1. 在 `Model/QRCodeParser.js` 中保留 `toBuffer()`、`download()`、`checkSize()` 的外部语义，新增元数据检查与方向/色彩归一化。
2. 将单次 `readBarcodes()` 拆为可测试的候选解码函数，统一 ZXing 选项和结果清洗。
3. 实现惰性的分级候选流水线：原图、增强图、截图裁剪、二值化、定位及透视矫正。
4. 增加总预算、候选计数、成功早停、Buffer 生命周期控制和异常隔离；某个增强策略报错时继续可用策略，而非让整次解析崩溃。
5. 如阶段 A 证明必要，再接入本地 fallback 解码器，并把其初始化成本延迟到 ZXing 失败之后。

### 阶段 C：接入与提示优化

1. 在 `Apps/QRCodeParser.js` 中根据模型返回的失败类别给出精确提示，成功回复保持现有单码/多码格式。
2. 确认同消息、引用消息、上下文补图路径仍传递原始图片 URL/文件，不在入口层重复下载或预处理。
3. 对引用消息结构缺失、图片过期、下载超时和非图片响应做回归验证。

### 阶段 D：测试、性能与回归

1. 运行清晰码、困难码、用户样本、多码、无二维码、损坏输入及超限输入测试。
2. 统计普通二维码快速路径与困难样本完整路径耗时，调整候选优先级和上限。
3. 做连续多图压力测试，确认内存可回落、WASM 只初始化一次、失败不会污染下一次解析。
4. 检查语法、依赖锁文件和 README 使用说明；若新增依赖，验证项目支持平台均可安装与运行。

## 预计文件改动

- `Model/QRCodeParser.js`：图像元数据校验、候选流水线、区域/几何处理、资源预算、结果归一化。
- `Apps/QRCodeParser.js`：按失败类别优化回复，保持现有命令和成功输出兼容。
- `package.json` 与锁文件：仅在技术验证证明必要时增加本地 fallback 解码依赖。
- 测试文件与 fixtures：新增标准码、困难码、用户样本及负例。
- `README.md`：说明支持场景、输入限制以及困难图片的建议。

## 验收标准

### 正确性

- [ ] 经独立扫码器确认有效后，用户提供的整屏艺术二维码截图能直接识别出与 ground truth 完全一致的内容；不得要求用户手工裁图作为通过条件。
- [ ] 清晰二维码、90/180/270 度旋转、反色、低对比度、轻度模糊、截图小码和透视码测试均得到正确内容。
- [ ] 单图多个二维码仍能全部返回并按文本去重；相同内容出现在不同增强候选中只返回一次。
- [ ] 中文、URL、纯文本和二进制可表示内容不被错误转码或截断。
- [ ] 无二维码图片不会误报；疑似艺术码但校验失败时绝不返回猜测内容。

### 兼容性与安全

- [ ] Buffer、HTTP(S)、`base64://`、Data URL、普通文件路径和 `file://` 输入行为不回退。
- [ ] `#识别二维码`、`识别二维码`、`解析二维码` 的同消息、引用和补发交互均通过。
- [ ] 15 MB 下载限制、下载超时、内容类型校验继续有效；超大像素图不会造成失控内存使用。
- [ ] 二维码载荷仅作为文本回复，不自动请求载荷 URL；日志不包含完整载荷和原图。

### 性能与稳定性

- [ ] 普通清晰二维码命中原图快速路径，不生成后续增强候选；性能相对现状无明显回退。
- [ ] 困难图片在预设总时限和候选上限内结束，超限时返回可操作提示。
- [ ] 连续处理成功、失败和损坏图片不会崩溃、泄漏未处理 Promise 或导致 WASM 重复初始化。
- [ ] 所有新增自动化测试通过，现有二维码生成及其他插件功能不受影响。

## 风险与应对

- **样本可能不是可解码的标准 QR**：先建立独立扫码器 ground truth；若无载荷，验收转为准确诊断并向用户索取原图，禁止用误码“通过”。
- **预处理组合导致 CPU/内存放大**：采用惰性候选、串行早停、像素/数量/时间三重预算。
- **固定阈值对不同图片泛化差**：以局部二值化和定位校正为主，固定阈值仅保留少量经样本矩阵验证的档位。
- **新增识码依赖过重或跨平台失败**：先做隔离 PoC；优先纯 JS/WASM，保留 ZXing 快速路径，并用支持平台安装测试作为合入门槛。
- **艺术化图案产生误码**：只接受解码器通过 QR 纠错/校验的结果，多引擎结果冲突时不自动选择未经证实的文本。

## 完成定义

上述验收项全部满足，用户样本的结果有 ground truth 佐证，性能预算有测试数据，README 与失败提示同步更新，且计划状态更新为“已完成”后，本优化任务方可关闭。
